# Bump brscan5 to 1.7.0 and harden the download

## Context

The daily image build failed again on the brscan5 step. `build_files/bazzite/build.sh`
pinned the RPM URL to version 1.6.2, and Brother removed that file from their CDN
after releasing 1.7.0.

This is the third occurrence of the same failure mode (1.5.1 → 1.6.2 in
`spec/2026-07-07-11-brscan5_bump_to_1_6_2.md`, and now 1.6.2 → 1.7.0). The
diagnosis is identical each time: the `curl` invocation used `-Lo` without `-f`,
so the CDN's "Not found" response — a 10-byte body — was written to
`/tmp/brscan5.rpm` with a zero exit status. The failure surfaced one step later,
as `error: open of Not failed` from `rpm -Uvh`, which points at the RPM rather
than at the HTTP 404 that actually caused it.

## Alternatives Considered

- **Vendor the RPM in the repo**: would make the build hermetic and immune to CDN
  churn, but adds a ~1.2 MB binary to git history for every driver release and
  means manual license/tracking work on each bump. Rejected for now.
- **Fetch from a trusted distro mirror (AUR/Void)**: AUR tracks 1.7.0, but Void
  Linux's `brother-brscan5` template still pins 1.6.2, so neither is a version
  oracle we can follow blindly.
- **Use a floating `latest` URL**: Brother serves no version-independent
  filename or redirect; the filename embeds the version. The download ID
  (`dlf104036`, x86_64) is stable across releases, but the basename is not.
- **Add a checksum verification step**: pins content and would also catch an HTML
  error page, but requires updating a hash on every bump and still does not fix
  the silent-404 behaviour. Deferred; `-f` covers the actual failure.

## Rationale

1.7.0 is the current release and is served from the same stable download ID as
before (`https://download.brother.com/welcome/dlf104036/`). Verified for this
change:

- HTTP 200, `brscan5-1.7.0-0.x86_64.rpm`, 1,256,770 bytes
- sha256 `197f63a52e89b8744f5a3c2d843abb3b76d003d5d4830bdfe675c44841a6c72b`
- `rpm -qp` reports `brscan5-1.7.0-0.x86_64`
- the four `libLxBs*` payload filenames are byte-for-byte the same names as in
  1.6.2, so the `/usr/lib64` link-chain block in `build.sh` needs no change
- dependencies are unchanged, including `libgtk-x11-2.0.so.0`, so the existing
  `dnf5 install -y gtk2` prerequisite still stands

Fixing the download flags is the part that matters beyond this one version: with
`-f`, a future removal fails immediately with curl's exit 22 (plus the HTTP
status), instead of producing a plausible-URL-but-garbage file and a misleading
RPM parser error.

## Requirements

1. Point the download URL in `build_files/bazzite/build.sh` at
   `brscan5-1.7.0-0.x86_64.rpm`.
2. Make the download fail fast on HTTP errors: `curl -fsSL --retry 3 -o ...`.
3. Leave the `libLxBs*` link-chain block and the `brsanenetdevice.cfg` handling
   untouched — both remain valid for 1.7.0.
4. Update current-version references in `spec/2026-05-31-08-brscan5_scanner.md`.
5. Keep the historical narrative in the older specs (1.5.1 and 1.6.2 bumps,
   runtime-links spec) as written; they describe the state at the time.
6. `shellcheck` must stay clean.

## Technical Approach

Single-line URL bump plus a hardened `curl` invocation in the scanner block. No
packaging, post-install, or link changes. Because `-f` is now used and the file
is consumed directly by `rpm -Uvh`, a missing release aborts the image build with
a curl error naming the URL — the correct blast radius.

## Issues & Resolutions

- **Silent 404 poisoning the RPM**: the root cause of all three failures. `curl`
  without `-f` treats HTTP 404 as success. Resolved by `-f` (and `--retry 3` for
  transient CDN errors); the comment above the block records the reasoning so it
  is not "cleaned up" back to `-Lo`.
- **Misleading error message**: the build log showed an RPM problem
  (`error: open of Not failed`) rather than a download problem, which sends
  debugging in the wrong direction. `-f` moves the failure to the actual cause.
- **Void Linux is a stale version oracle**: its template still pins 1.6.2, so
  copying the "distro consensus" version — the method used for the 1.6.2 bump —
  would have re-pinned a dead URL. Check the CDN directly (HTTP status, size,
  `rpm -qp`) rather than trusting a downstream packager.
- **Repeated root cause, no upstream fix**: Brother will keep deleting old
  releases. Expect this bump again; if the churn becomes painful, revisit
  vendoring the RPM or verifying a recorded sha256 in the build script.
